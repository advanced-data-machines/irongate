Install a gateway.
Configure. Verify. Operate.

First draft for a dedicated Linux gateway with one subscriber network, a local HTTPS captive portal and an existing RADIUS service.

Design preview — not executable installation instructions. Release packages, the system service and host-network apply/rollback commands below do not exist yet. Today’s working gateway runs only in the isolated QEMU lab. This guide defines the installation experience we intend to build.

1 Prepare an isolated gateway

Use a dedicated x86-64 Linux appliance with systemd, two Ethernet interfaces and local console access. Keep management reachable independently of subscriber forwarding. Select the supported OS/version and capacity from a qualified release profile; that matrix is still to be established.

Begin on an isolated test LAN. Do not replace the production default gateway. Identify existing DHCP servers, interface managers and firewall rules before applying a configuration. Do not connect two DHCP servers to the same subscriber LAN.

2 Install the release package — proposed

Obtain the exact version/architecture package and published verification material from the future IronGate release channel. Verify its provenance and checksum before installation. No deployment package or download URL is published by this draft.

# Future package name and installation example — not available today
sudo apt install ./irongate_VERSION_amd64.deb

The proposed package installs ig, irongated, a commented configuration and a systemd unit. Installation should leave forwarding inactive until the administrator reviews and applies the network plan. A static-musl binary does not remove Linux/kernel or service prerequisites.

3 Complete the site configuration

Proposed location: /etc/irongate/irongate.toml. The package should provide a complete example. Record explicit values for:

SettingIllustrative value / operator decision
Interfaces and LANUplink enp1s0, subscriber enp2s0; 192.168.50.1/24; DHCP .20–.250. Confirm actual names and subnet conflicts.
Upstream and DNSDeclare uplink addressing/default route and DNS. Select and verify the supported routed/NAT behavior; this deployment path is not implemented.
Local HTTPS portalChoose a real hostname, trusted certificate/key and client DNS resolution. Define certificate renewal ownership. Arbitrary HTTPS requests are not intercepted.
RADIUS and accountingServer endpoint/transport, NAS identity and source IP, secret-file path, authentication method and interim interval. Register this NAS on the backend.
Limits and ownershipChoose tested session/memory limits, session/idle timeouts, IPv6 containment and managed or administrator-preconfigured host resources.

Store passwords, shared secrets and private keys outside TOML, readable only by the required service identity. Production HTTPS settings, protected backend transport and full runtime schema still need implementation/qualification. External/cloud portal deployment is outside this first walkthrough.

4 Validate and review the network plan

Available today: the CLI supports offline example-profile validation and passive Linux interface preflight. A successful result does not establish runtime readiness.

ig config check --config /etc/irongate/irongate.toml
ig doctor --config /etc/irongate/irongate.toml

Proposed: review every address, route, DHCP owner and persistent guard change before applying. The plan must identify its effect on management access and the rollback path.

# Proposed commands — not implemented
ig plan --config /etc/irongate/irongate.toml
sudo ig apply --plan setup.json
sudo systemctl enable --now irongated

The future plan command should produce setup.json; apply must revalidate it against current host state. First activation requires a local console and a tested recovery path. The package must not silently take over unrelated interfaces or firewall resources.

5 Prove access from a subscriber

ProcedureExpected result
Connect a test deviceObtain an address, gateway and DNS from the selected profile. Upstream transit remains blocked before login.
Open the portalUse the documented portal URL; HTTPS validates without bypassing certificate warnings. Automatic discovery/HTTP redirection must be tested separately.
Sign in and transfer dataA valid account permits bidirectional transit. A rejected account stays blocked. Backend records show matching session identity and directional cumulative usage.
Log out and expire a sessionBoth existing and new transit stop. A Stop record is delivered or clearly retained as pending; backend delay cannot hold access open.
Exercise an outageExisting users retain their granted limits/expiry. New authentication fails closed; known accounting failure pauses admissions. Restore the backend and verify backlog recovery.

A running process is not proof of enforcement. Use an independent subscriber, backend records and counter identities. Production qualification must also cover restart behavior, IPv6 bypass, NIC behavior and the intended load.

6 Operate and recover — proposed

# Proposed operational commands — not implemented
ig status --json
ig verify --config /etc/irongate/irongate.toml
ig support export --output support.json

Status should separate enforcement, portal, authentication and accounting health. Verification actively creates test traffic; support exports should redact secrets and subscriber identifiers by default. Runtime ig doctor integration remains to be built.

Rollback: keep the previous package/configuration and management path available. Restore only IronGate-owned host changes using the future recorded rollback procedure. Stopping the service must leave subscriber transit blocked; it must not flush the host firewall or open unrestricted forwarding. Package downgrade alone is not a complete network rollback.

Before this becomes an install guide Deliver and test packaging/service startup, complete runtime TOML, safe apply/rollback, portal certificates/discovery, uplink routing/NAT, passive runtime diagnostics and documented accounting restart/storage behavior. Today’s accounting outbox is volatile: pending records may be lost on a crash. No production capacity is qualified.
