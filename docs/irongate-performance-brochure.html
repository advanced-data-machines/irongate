IronGate
Architecture and performance brief · November 2026

Network authentication
and access enforcement

A Rust successor to CoovaChilli, designed to make captive access easier to configure, observe and test. The gateway owns the access decision whether the portal is on the device or in the cloud.

Early development. Configuration checks, passive diagnostics and an offline DHCP protocol pilot exist. The live gateway, portal, RADIUS client and enforcement path below are planned.

How a client gains access — planned flow

01 / JOIN

Identify the network

Ingress interface and VLAN select the profile. DHCP assigns an address; a lease alone grants no upstream access.

02 / RESTRICT

Allow only bootstrap traffic

Permit the declared DHCP, DNS and portal paths. Other subscriber transit is denied before admission.

03 / PRESENT

Open the selected portal

Serve a local page or use a separate LAN/cloud frontend. External tenant, site and gateway scope stays explicit.

04 / DECIDE

Use the configured provider

Local consent grants the configured policy without identity proof. RADIUS can validate credentials and return supported policy attributes.

05 / ENFORCE

Commit the access change

Bind the decision to a live session generation, reserve accounting capacity and apply policy before confirming access.

06 / ACCOUNT AND REVOKE

Keep the result observable

Track traffic and accounting health. Logout or expiry removes access without waiting for a remote accounting response.

A valid cloud callback or RADIUS response is a control event, not a substitute for verified packet enforcement. Browser credentials require HTTPS; arbitrary HTTPS sites are not intercepted.

Did CoovaChilli use iptables?

Yes, alongside substantial C userspace logic. In the classic path, subscriber state checks and DNAT decisions run in dhcp.c; callbacks in chilli.c perform accounting and optional rate checks. Traffic then passes through TUN/TAP to Linux routing and firewall processing. Setup scripts install iptables rules. Optional kernel/netfilter paths also exist.

ResponsibilityProposed IronGate placement
Client access decisionsPortable Rust session and policy code, with explicit counters, expiry and revocation.
Linux safety boundaryA small persistent deny guard, likely nftables, to block alternate kernel/bridge/IPv6 bypass paths.
Device and OS integrationThin packet I/O, clock, socket and host-network adapters. Exact forwarding backend must pass the VM experiment.

Performance must be demonstrated: Rust owns subscriber policy; Linux supplies necessary platform services and a fail-closed boundary. Compare matched workloads and verify the complete client path on a declared deployment profile.

The packet path and the evidence

The code that matters
on every packet

The performance-critical path is validation, network/session lookup, policy evaluation and forwarding or drop. Login pages and backend requests belong outside that repeated work.

Borrow and validate
→
Bind network/client
→
Evaluate policy
→
Forward or drop

Proposed Rust-like pseudocode. This illustrates the future enforcement boundary; these functions are not shipping runtime code.

let packet = validate_borrowed(frame)?;
let network = classify_ingress(interface, packet.vlan())?;
if bootstrap.permits(network, &packet) {
    return handle_bootstrap(network, packet);
}
let session = sessions.match_bound_client(network, &packet)?;
let decision = policy.evaluate(session, &packet, now)?;
forward_or_drop(decision, packet)

Bound the fast path

Borrow input bytes; reuse startup-owned packet and session slots. Bound lookups, queues and work per dispatch. Validate before field access and use generations to reject stale results after slot reuse.

Keep blocking I/O, disk writes, formatted logs and per-packet heap growth out of the packet owner. Return traffic must resolve to the same network/session policy.

Keep control work separate

Portal actions and RADIUS exchanges update session decisions asynchronously. Ordinary data packets do not ask the RADIUS server for permission.

Bounded workers handle journal/accounting delivery. Reserve progress for expiry, revocation and diagnostics even under forwarding load; a slow backend must not stall every subscriber.

What is implemented and measured today?

The current irongate-proto::parse_request composes borrowed Ethernet/VLAN, IPv4/UDP and DHCP validation. It verifies lengths and available checksums; the OFFER encoder writes into caller-owned storage. The crate is no_std, imports no allocator and has no dependencies.

EvidenceResult and boundary
Rust parser + OFFER replay100,000 tagged DISCOVER/OFFER replays: zero additional measured heap allocations after identical setup/warmup.
Original C versus Rust18 option cases and 4 OFFER cases checked; independent wire validation and C ASan/UBSan passed. Both encoders showed no additional heap allocation in replay.
Relative speed and capacityNo overall winner established. Current output/instrumentation differs; gateway throughput, tail latency and session capacity are not yet measured.

Counters distinguish received, permitted, submitted-for-transmit and dropped traffic. Accounting acknowledgements and delivered client traffic require separate evidence.

Validate the full client journey

In an isolated VM: prove blocked traffic before login, usable bidirectional access after login, and blocked existing/new flows after logout or expiry. Repeat for local and external portals, RADIUS outages and two VLANs. Measure packet rate, p99 latency, allocation/churn stability, accounting lag and diagnostic overhead on a declared profile.
